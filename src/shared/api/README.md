# src/shared/api

서버 호출이 전부 거치는 폴더다. 규칙과 그 이유는 `.agents/rules/api.md`에 있다. 이 문서는 폴더에 무엇이 들어가고 무엇이 아직 정해지지 않았는지를 적는다.

지금은 이 README만 있다. 구현은 API 레이어 담당이 정한다.

## 들어갈 것

- fetch 래퍼
- 공통 에러 타입
- 쿼리 키 규칙
- 서버 응답의 공통 타입

기능별 엔드포인트 호출과 그 응답 타입은 여기 두지 않는다. `src/features/{기능}/api`에 둔다.

## 파일 배치 제안

| 파일            | 담는 것                                 |
| --------------- | --------------------------------------- |
| `client.ts`     | fetch 래퍼. 기본 주소와 헤더, 응답 해석 |
| `errors.ts`     | 공통 에러 타입                          |
| `query-keys.ts` | 쿼리 키 규칙                            |
| `types.ts`      | 서버 응답의 공통 타입                   |

제안이다. 담당이 바꿀 수 있고 바꾸면 이 표를 함께 고친다.

## 아직 정해지지 않은 것

응답 형식은 백엔드가 정한 것을 그대로 쓴다. 프론트가 원하는 모양을 들고 가서 협의하지 않는다. 형식을 두고 다투는 비용이 얻는 것보다 크고 camelCase와 snake_case 같은 차이는 어느 쪽이든 프론트에서 흡수할 수 있다. 대신 둘이 필요하다. 백엔드 세 사람이 같은 모양으로 내려주는 것과 Swagger 스펙 공유다. 엔드포인트마다 형식이 다르면 맞추는 비용이 전부 프론트로 오고, 스펙 파일이 있으면 타입을 손으로 옮겨 적지 않고 생성할 수 있다.

아래 여섯 항목은 미정이다. 백엔드 저장소에 아직 코드가 없어 응답 형식을 코드에서 확인할 수도 없다. 백엔드가 정하면 이 표와 `types.ts`를 먼저 고치고 코드를 그에 맞춘다. 그 전에는 그럴듯한 기본값을 채우지 않는다.

| 항목             | 정해지면 적을 것                  |
| ---------------- | --------------------------------- |
| 응답 공통 구조   | 성공 응답과 실패 응답의 겉모양    |
| 에러 코드 체계   | 에러 코드와 HTTP 상태 코드의 규칙 |
| 날짜와 시간 포맷 | 문자열 형식과 타임존              |
| 페이지네이션     | offset 또는 cursor                |
| 필드 이름 규칙   | camelCase 또는 snake_case         |
| 스펙 문서 위치   | Swagger 스펙을 어디서 받는가      |

`NEXT_PUBLIC_API_BASE_URL` 값도 아직 없다. 백엔드 배포 방식이 정해지면 나온다.
