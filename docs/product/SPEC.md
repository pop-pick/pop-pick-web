# 팝픽 기능 명세

기능이 정확히 어떻게 동작하는지 적는 문서다. 왜 만드는지는 PRD.md가 맡는다. 구현하다 규칙이 바뀌면 이 문서를 먼저 고치고 코드를 맞춘다. 화면과 기능의 정본은 2026-09-12 피그마 화면이고 상태의 원천과 데이터 모델, 경계의 계약은 `docs/architecture/`에 있다.

## 용어

프로젝트 고유 용어를 정의한다. 코드 식별자와의 대응을 함께 적어 문서와 코드를 오갈 수 있게 한다. 식별자는 `docs/architecture/`가 정한 타입 이름이고 서버 응답 타입은 백엔드 계약이 정해진 뒤에 만든다. 파일 경로가 붙은 것만 지금 코드에 있다.

| 용어      | 뜻                                                                                              | 코드에서                                                                                        |
| --------- | ----------------------------------------------------------------------------------------------- | ----------------------------------------------------------------------------------------------- |
| 팝업      | 기간과 장소가 정해진 팝업 스토어. 팝픽이 다루는 기본 단위. 브랜드와 캐릭터 IP 팝업까지다        | `PopupSummary`, `PopupDetail`. 카드가 그리는 값만 담은 `PopupCardItem`(`shared/model/popup.ts`) |
| 온보딩    | 첫 진입에서 동행 유형과 인원수, 관심 카테고리와 지역, 선호 활동과 자유 입력을 받는 세 단계 화면 | `OnboardingAnswers`                                                                             |
| 미리보기  | 카테고리별 취향 스코어와 예시 팝업. 로그인이 앞으로 오면서 존치 여부가 미결정이다               | 미정                                                                                            |
| 코스      | 팝업 여러 곳의 방문 순서와 도착 시각, 구간별 도보 소요시간. 원데이 플래너가 만든다              | `Course`, `CourseItem`                                                                          |
| 구간      | 코스 안에서 이어지는 팝업 두 곳 사이의 도보 이동                                                | `WalkSegment`                                                                                   |
| 추천 이유 | AI가 그 팝업이나 코스를 추천한 까닭을 적은 문구. 두 줄 이내                                     | `RecommendedPopup.reason`, `Course.aiReason`                                                    |
| 찜        | 팝업을 관심 팝업으로 저장하는 것                                                                | `PopupSummary.isBookmarked`                                                                     |
| 지역      | 팝업이 속한 상권. 성수, 여의도, 홍대, 신촌, 용산 다섯                                           | `Region`, `REGION_LABELS`(`shared/model/region.ts`)                                             |

## 화면 흐름과 라우트

Next.js App Router 라우트 경로다. 폴더 구조와 라우트 그룹은 `docs/architecture/ARCHITECTURE.md`에 있다.

| 경로                          | 화면               | 로그인    | 하단 탭바 |
| ----------------------------- | ------------------ | --------- | --------- |
| `/`                           | 랜딩               | 아니오    | 없음      |
| `/onboarding/1`, `/2`, `/3`   | 온보딩 세 단계     | 아니오    | 없음      |
| `/onboarding/result`          | 추천 미리보기      | 미결정    | 없음      |
| `/login?next=`                | 로그인             | 아니오    | 없음      |
| `/auth/kakao/callback`        | 카카오 로그인 콜백 | 아니오    | 없음      |
| `/home`                       | 홈. 회원과 비회원  | 아니오    | 있음      |
| `/explore`                    | 탐색 지도와 목록   | 아니오    | 있음      |
| `/popups/{popupId}`           | 팝업 상세          | 아니오    | 없음      |
| `/planner`                    | 플래너 조건 입력   | 만들기 때 | 있음      |
| `/planner/generating/{jobId}` | 코스 생성 중       | 예        | 없음      |
| `/courses/{courseId}`         | 코스 결과          | 예        | 없음      |
| `/courses/{courseId}/saved`   | 캘린더 저장 완료   | 예        | 없음      |
| `/my`                         | 내 팝업            | 예        | 있음      |

구글 콜백 `/auth/google/callback`은 아직 만들지 않았다. 라우트가 아닌 화면이 둘 더 있다. 렌더링이 실패하면 `error.tsx`가 받고 없는 경로는 `not-found.tsx`가 받는다.

첫 방문의 흐름은 랜딩에서 로그인을 하고 온보딩 세 단계를 지나 홈으로 간다. 랜딩의 "둘러보기"는 로그인과 온보딩 없이 비회원 홈으로 간다. 재방문자에게 랜딩을 매번 보일지는 미정이다.

로그인이 필요한 동작을 비로그인 상태에서 누르면 그 시점에 로그인 화면으로 가고 끝나면 누른 자리로 돌아온다. 찜과 코스 만들기가 그렇다. 내 팝업은 화면 전체가 로그인 필요다.

## 기능 상세

### 온보딩 취향 수집

**동작 규칙.**

1. 세 단계다. 1단계는 동행 유형(혼자, 친구, 연인, 가족)과 인원수(1명, 2명, 3명, 4명 이상), 2단계는 관심 카테고리(다중)와 자주 가는 지역(다중), 3단계는 선호 활동(굿즈 구경, 사진 찍기, 체험하기, 맛있는 것 먹기. 다중)과 자유 입력이다
2. 1단계와 2단계에 건너뛰기가 있다. 건너뛴 단계의 값은 비어 있다
3. 자유 입력은 200자까지다. 남은 글자 수가 보인다
4. 온보딩에 들어오기 전에 로그인을 받는다. 랜딩의 "나에게 맞는 팝업 찾기"가 로그인으로 보내고 성공하면 1단계로 온다
5. 마지막 단계를 마치면 답이 서버에 저장되고 홈으로 간다
6. 저장한 취향은 플래너 조건 입력과 마이페이지에서 다시 고칠 수 있다

**데이터.** 로그인한 사용자가 답하므로 답은 서버가 갖는다. 입력 중인 값만 스토어에 있고 마치면 비운다. 저장이 실패하면 화면에 드러내고 다시 시도할 길을 준다. 상세는 `docs/architecture/onboarding.md`.

**경계 조건.** 브라우저가 로컬 저장을 막으면 새로고침 때 답이 사라진다. 이때 3단계에 그 사실을 안내한다.

### AI 개인화 추천 코스

**동작 규칙.**

1. 추천 생성과 이유 문구는 백엔드가 한다. PM이 정의한 기준 위에서 AI가 돈다. 프론트엔드는 결과를 그린다
2. 홈 추천 카드에는 대표 이미지, 찜 버튼, 예약 배지와 카테고리 배지, 팝업명, 지역과 종료일, 추천 이유가 있다. 추천 이유는 두 줄 이내이고 넘치면 두 줄에서 말줄임한다
3. 추천이 준비되기 전(취향이 없거나 서버가 준비 중 상태를 보냄)이거나 조회가 실패하면 그 섹션을 인기 팝업으로 채우고 섹션 제목과 한 줄 문구를 바꿔 추천이 아님을 보인다. 다시 시도 버튼을 둔다. 이 축소 동작은 로그를 남긴다. 인기 팝업까지 실패하면 실패를 그대로 보인다
4. 비회원 홈은 취향 입력을 권하는 배너와 인기 팝업 목록이다

**데이터.** 추천 결과는 구조화된 팝업 목록과 이유 문구로 온다. 응답 형태와 백엔드 요구는 `docs/architecture/recommendation.md`.

**경계 조건.** 추천 이유의 글자 수 상한은 백엔드와 맞춘다. 상한과 무관하게 두 줄 말줄임은 남는다.

### 팝업 탐색과 지도

**동작 규칙.**

1. 지도 뷰와 목록 뷰를 전환한다. 검색어와 필터, 정렬은 뷰를 바꿔도 그대로다. 원천이 URL이라 새로고침과 공유 링크에서도 같다
2. 필터는 지역(단일), 카테고리(단일), 예약 없이 입장, 이번 주 종료 넷이다. "예약 없이 입장"은 예약 유형이 자유입장이나 현장대기인 팝업이다. "이번 주 종료"는 종료일이 오늘부터 7일 안인 팝업이다
3. 검색은 팝업명과 브랜드를 대상으로 하고 입력이 멈춘 뒤 300ms에 한 번 반영된다
4. 목록 뷰는 "총 N곳"과 정렬(종료 임박순, 최신순, 인기순)을 보이고 열 개 단위 무한 스크롤이다
5. 지도 뷰는 같은 조건의 팝업을 최대 50개까지 번호 마커로 보인다. 마커를 누르면 바텀 카드가 그 팝업을 보이고 카드를 누르면 상세로 간다
6. 결과가 없으면 적용한 필터를 칩으로 보이고 필터 초기화 버튼과 가까운 지역의 건수를 제안한다
7. 지도는 카카오맵 JavaScript SDK로 그린다

**경계 조건.** 마커 수 상한은 50이다. 백엔드 페이지 상한과 같다. 지도 SDK 로딩이 실패하면 원인 문구와 목록 뷰로 가는 버튼을 보인다.

**데이터.** 팝업 한 건의 필드 목록은 `docs/architecture/popup.md`에 있다. 백엔드 `popup` 테이블에 없는 예상 체류시간과 확인 상태는 요구 목록에 있다.

### 팝업 상세 정보

**동작 규칙.**

1. 전체 화면이다. 헤더에 뒤로 가기와 팝업명이 있다
2. 운영 시간은 "매일 오전 11시부터 오후 8시까지, 월요일 휴무" 한 줄로 합쳐 보이고 예상 체류시간은 "40분에서 60분" 범위로 보인다. 이미지 갤러리는 스와이프와 이전, 다음 버튼으로 넘긴다. 배치는 `docs/design/DESIGN-SPEC.md`에 있다
3. 탭이 셋이다. 상세 정보, 방문 후기, 위치와 주차. 방문 후기는 데이터가 오기 전까지 준비 중 상태를 보인다
4. 하단 액션은 찜과 "이 팝업으로 AI 코스 추천받기"다. 후자는 플래너 조건 입력으로 가며 그 팝업의 지역이 미리 선택되고 코스에 그 팝업이 들어간다
5. 예약 링크가 있는 팝업은 정보 영역에 외부 예약 사이트로 가는 링크를 보인다. 예약은 사이트 안에서 받지 않는다
6. 길찾기는 카카오맵 웹 링크를 새 탭으로 연다
7. 신뢰도가 낮은 데이터는 감추지 않고 "정보 확인 중" 배지와 안내 배너로 보인다
8. 대표 이미지가 없으면 카테고리별 대체 이미지를 쓴다

**경계 조건.** 값이 없는 요소(예상 체류시간, 후기, 조회수, 예약 링크)는 그 줄을 그리지 않는다. 주소 복사가 실패하면 주소를 선택 가능한 텍스트로 두고 실패 문구를 보인다.

**데이터.** 공유 링크의 메타 태그(제목, 대표 이미지, 기간)는 서버가 채운다. 상세는 `docs/architecture/popup.md`.

### 관심 팝업 저장

**동작 규칙.**

1. 카드와 상세, 마커 카드의 하트를 눌러 찜하고 다시 눌러 해제한다
2. 하트는 서버 응답을 기다리지 않고 바로 바뀐다. 서버가 실패하면 되돌리고 실패 문구를 보인다
3. 같은 팝업이 여러 화면에 보여도 하트 상태가 같다
4. 비로그인 사용자가 누르면 로그인 화면으로 가고 끝나면 누른 자리로 돌아온다. 누른 찜은 되어 있지 않다
5. 내 팝업의 찜한 팝업 탭에 찜 목록이 있다. 종료된 팝업은 지우지 않고 흐리게 보이고 종료 임박 배지가 붙는다

**데이터.** 찜은 서버 상태다. 상세는 `docs/architecture/bookmark.md`.

### 원데이 플래너

**동작 규칙.**

1. 조건은 지역(다섯 중 하나), 방문 날짜, 시작 시각, 머무는 시간(간편 약 2시간, 반나절 4시간에서 5시간), 동행(혼자, 연인, 친구, 가족), 동선 세부 옵션 토글 둘(체험형 액티비티 포함, 식사와 카페 동선 포함)이다. 지정한 지역 안에서만 동선을 짠다. 날짜와 시작 시각은 피그마 조건 입력에 없고 9/6 제출문과 IA에 있어 FE가 넣었다. PM 확인 항목이다
2. 코스 만들기는 로그인이 필요하다. 비로그인이면 조건 입력은 보이되 만들기 버튼에서 로그인으로 간다
3. 코스 생성은 비동기 작업이다. 만들기를 누르면 생성 중 화면이 바로 보이고 단계별 체크리스트(취향에 맞는 팝업 고르기, 도보 동선 계산하기, 시간표 맞추기)가 1초 간격으로 갱신된다. 취소 버튼이 작업을 멈춘다. 60초 안에 끝나지 않으면 실패로 보이고 다시 시도와 조건 수정을 준다
4. 생성이 끝난 코스는 그 순간 저장된다. 별도 저장 버튼이 없다. 다시 만들기는 같은 조건으로 새 코스를 만들고 이전 코스는 남는다
5. 코스는 팝업 여러 곳과 방문 순서, 도착 시각으로 이뤄진다. 방문 순서는 최적화하지 않는다
6. 이어지는 팝업 두 곳마다 도보 소요시간을 따로 조회한다. 팝업 세 곳이면 두 번, 네 곳이면 세 번이다. 경유지로 묶어 한 번에 부르면 구간별 시간을 따로 못 받는다
7. 도보 소요시간은 카카오맵 REST API 도보 경로 조회에서 온다. 어림값이 아니라 실제 경로 기반이다. 소요시간은 초 단위로 오므로 분으로 바꿔 보여준다. 함께 오는 경로 좌표를 지도에 선으로 그린다. 경로 조회는 코스의 방문 순서를 아는 백엔드가 부른다
8. 코스 결과는 지도에 번호 마커와 경로선을 그리고 타임라인에 도착 시각과 예상 체류시간, 다음 장소까지의 도보 시간과 거리를 보인다. 배치는 `docs/design/DESIGN-SPEC.md`에 있다
9. 내 팝업의 저장한 코스 탭에서 코스를 다시 열고 삭제한다. 삭제는 확인을 거친다

**경계 조건.** 경로 조회는 실패해도 HTTP 200이 오고 응답의 상태 값만 바뀐다. 같은 좌표이거나 너무 멀거나 경로를 못 찾는 경우가 있다. 실패한 구간은 소요시간 자리에 분 수 대신 "소요시간 모름"을 보여준다. 0분이나 빈 값으로 바꾸지 않는다. 그 구간 뒤의 도착 시각에는 "예상" 라벨이 붙는다. 코스를 다시 열면 소요시간을 다시 조회하므로 구간마다 로딩 표시를 먼저 그린다. 코스의 팝업과 순서는 먼저 그려지고 구간 소요시간은 별도 요청으로 뒤에 채워진다.

**데이터.** 코스는 팝업 ID와 방문 순서, 도착 시각, 조건을 저장한다. 소요시간은 열 때마다 다시 조회하고 경로 응답은 저장하지 않는다. 카카오가 REST API 응답의 임시 저장을 허용하지 않는다. REST API 키는 브라우저에 두지 않는다. 상세는 `docs/architecture/planner.md`와 `docs/architecture/course.md`.

### 소셜 로그인

**동작 규칙.**

1. 구글과 카카오 중 하나로 로그인한다. 카카오 버튼이 위다. 별도 약관 동의 화면 없이 버튼 아래 고지문으로 갈음한다. 지금 동작하는 것은 카카오뿐이고 구글은 클라이언트 ID와 콜백 경로가 없어 비활성 버튼으로 자리만 있다
2. 프론트엔드가 공급자에서 인가 코드를 받아 백엔드에 넘기고 백엔드가 토큰 교환과 사용자 저장을 한 뒤 우리 액세스 토큰과 리프레시 토큰을 준다
3. 토큰은 브라우저 메모리에만 둔다. 새로고침하면 로그아웃 상태다. 백엔드가 리프레시 토큰을 httpOnly 쿠키로 주기 시작하면 앱 시작 때 세션을 되살린다
4. 액세스 토큰이 만료되면 사용자가 모르게 한 번 재발급하고 요청을 다시 보낸다. 재발급까지 실패하면 로그인 화면으로 간다
5. 로그인이 끝나면 `next`에 적힌 경로로 돌아간다. 없으면 홈이다
6. 공급자 화면에서 취소하면 "로그인을 취소했습니다"와 돌아가는 링크를 보인다

**경계 조건.** 인가 요청에 `state`를 실어 브라우저 세션 저장소에 두고 콜백에서 대조한다. 값이 다르면 교환하지 않는다. 인가 코드 교환은 코드를 키로 하는 조회라 코드 하나에 요청이 한 번만 나간다.

**데이터.** 닉네임과 프로필 이미지는 내 정보 조회로 받는다. 백엔드 엔티티에 아직 없어 요구 목록에 있다. 상세는 `docs/architecture/auth.md`.

### 캘린더 연동

**동작 규칙.**

1. 코스 결과의 캘린더 저장 버튼은 둘로 갈린다. 구글 캘린더는 일정 등록 링크를 새 탭으로 열고, 애플과 그 외 캘린더는 .ics 파일을 내려준다. 인증과 백엔드 작업이 없다. FE 제안이고 PM과 백엔드 확인 항목이다
2. 일정은 코스 하나에 하나다. 시작은 첫 도착 시각, 종료는 마지막 도착 시각에 예상 체류 최대를 더한 것이고 본문에 방문 순서가 들어간다
3. 저장 완료 화면은 "캘린더로 보냈습니다"이고 코스 요약과 "저장된 일정 보기", "홈으로" 링크가 있다. 등록 여부를 우리가 알 수 없어 "등록 완료"라고 쓰지 않는다
4. 저장한 코스 목록에 "캘린더에 보냄" 배지가 붙는다
5. 캘린더가 알림을 보내므로 서비스 안에 알림 기능을 두지 않는다

**경계 조건.** 캘린더에 보낸 시각을 서버에 기록하는 요청이 실패해도 캘린더 동작은 이미 끝났으므로 완료 화면으로 간다. 배지가 안 붙는 것만 로그로 남긴다.

**데이터.** 상세는 `docs/architecture/course.md`의 캘린더 절.
