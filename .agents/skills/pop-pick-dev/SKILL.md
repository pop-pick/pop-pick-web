# 팝픽 개발 하네스

작업을 계획과 구현, 리뷰 셋으로 나누고 필요한 만큼만 에이전트를 부른다. 게이트 명령과 룰 본문은 되풀이하지 않는다. 순서와 누구를 부를지만 적는다.

## 시작할 때 읽는 순서

1. 루트 `AGENTS.md`
2. 작업이 닿는 룰. 어느 룰이 무엇을 다루는지는 `AGENTS.md`의 룰 표에 있다
3. `docs/product/ROADMAP.md`의 미결정 절

명세나 화면 배치는 `docs/README.md`에서 어느 문서가 답하는지 찾는다.

## 에이전트

`.claude/agents/` 아래 네 폴더에 열하나다. 식별은 파일 위치가 아니라 `name`이다.

| 폴더         | 에이전트                                                                                                                                                          | 하는 일                                                                     |
| ------------ | ----------------------------------------------------------------------------------------------------------------------------------------------------------------- | --------------------------------------------------------------------------- |
| `builders/`  | `pop-pick-spec-navigator`                                                                                                                                         | 요구사항과 백엔드 계약을 정본에서 확정하고 문서와 코드가 다른 곳을 드러낸다 |
| `builders/`  | `pop-pick-architect`                                                                                                                                              | 바꿀 파일과 층 배치, 상태를 두는 곳, 공개 표면 영향을 정한다                |
| `builders/`  | `pop-pick-implementer`                                                                                                                                            | 승인된 범위 안에서 데이터 층과 화면을 만들고 게이트를 통과시킨다            |
| `verifiers/` | `pop-pick-integration-qa`                                                                                                                                         | 백엔드 계약과 설계 대비 동작을 경계에서 교차 비교한다                       |
| `curators/`  | `pop-pick-docs-curator`                                                                                                                                           | 구현이 바꾼 동작을 `docs/`에 옮긴다                                         |
| `reviewers/` | `pop-pick-review-structure`, `pop-pick-review-typescript`, `pop-pick-review-tailwind`, `pop-pick-review-screen`, `pop-pick-review-data`, `pop-pick-review-nextjs` | 룰을 하나씩 소유하고 스크립트가 못 잡는 판단을 한다                         |

리뷰어 여섯에는 `review-protocol` 스킬이 미리 실려 같은 모양으로 보고한다. 검수와 자문 두 모드가 거기 있다. 읽기 위주 셋(spec-navigator, architect, integration-qa)과 리뷰어는 코드를 고치지 않는다.

## 어디까지 부를지

**기본은 적게 부르는 쪽이다.** 전부 부르지 않는다. 규모는 바뀌는 것이 정한다.

| 규모           | 판정 기준                                                                                     | 부르는 에이전트                                                                      |
| -------------- | --------------------------------------------------------------------------------------------- | ------------------------------------------------------------------------------------ |
| 공개 표면 변경 | 라우트, 공용 컴포넌트 props, `shared/api` 시그니처, 화면이 분기하는 에러 코드가 늘거나 바뀐다 | 다섯 전부. spec-navigator, architect, implementer, integration-qa, docs-curator 순서 |
| 동작 변경      | 표면은 같고 동작이 바뀐다. 파일 셋 이상                                                       | spec-navigator, implementer, integration-qa                                          |
| 결함 수정      | 파일 한둘, 계약이 확정돼 있다                                                                 | implementer 뒤에 integration-qa                                                      |
| 골격과 문서    | 앱 소스를 건드리지 않는다                                                                     | 직접 고치고 게이트만                                                                 |
| 조사와 질문    | 코드 변경 없음                                                                                | 부르지 않고 직접 답한다                                                              |

리뷰어는 규모와 따로 바뀐 곳이 정한다. 도중에 미결정이 나오면 그때 멈추고 묻는다.

## 누구를 부를지

리뷰어는 바뀐 곳이 정한다.

```bash
git status --short
git diff -U0 -- src | grep -E '^\+.*(className=|export |"use (client|server)"|/\*\*)'
```

| 바뀐 곳                                                                    | 리뷰어                       |
| -------------------------------------------------------------------------- | ---------------------------- |
| 파일이 생기거나 옮겨지거나 지워졌다                                        | `pop-pick-review-structure`  |
| export가 생기거나 이름이 바뀌었다, JSDoc을 적었다                          | `pop-pick-review-typescript` |
| `className`이 바뀌었다, `globals.css`                                      | `pop-pick-review-tailwind`   |
| `features/*/ui`, `shared/ui`                                               | `pop-pick-review-screen`     |
| `features/*/api`, `hooks`, `model`의 스토어, `shared/api`                  | `pop-pick-review-data`       |
| `src/app`, `next.config.ts`, `"use client"`나 `"use server"`를 새로 붙였다 | `pop-pick-review-nextjs`     |

해당하는 곳이 없으면 부르지 않는다. 한 변경이 여러 줄에 걸리면 그 리뷰어를 다 부른다. 서로 판단하는 것이 다르다.

## 만들기 전에 자문할 때

리뷰어는 만들기 전에도 부를 수 있다. 질문 하나를 넘기고 룰의 어느 절에 해당하는지 답을 받는다.

- 시안 값이 여럿인 화면을 처음 옮길 때 `pop-pick-review-tailwind`에게 값 목록을 넘겨 토큰 대응표를 받는다
- 파일을 어디에 둘지 갈릴 때 `pop-pick-review-structure`
- 값을 어디에 둘지 갈릴 때 `pop-pick-review-data`

자문은 구현을 대신하지 않는다. 답을 받은 뒤 만드는 것은 implementer다.

## 실행 방식

Agent 도구로 서브 에이전트를 부르고 결과는 반환값으로 받는다. `name`을 붙여 부르면 `CLAUDE_CODE_EXPERIMENTAL_AGENT_TEAMS=1`인 대화형 세션에서는 팀원으로 뜨고 아니면 서브 에이전트로 돈다. 팀원에게는 정의의 `skills`가 실리지 않아서 리뷰어 본문이 규약 파일을 직접 읽으라고 적는다. `model`은 전부 opus다.

- 리뷰어는 한 번에 병렬로 부른다. 볼 파일이 겹쳐도 판단하는 것이 다르다
- 빌더 셋은 차례로 부른다. 앞 단계의 산출물을 다음 단계가 읽는다
- 리뷰어를 부를 때 바뀐 파일 목록과 스크립트 출력을 프롬프트에 넘긴다
- 보고는 반환값으로 받는다. 공개 표면 변경처럼 다섯을 다 부를 때만 `_workspace/{작업}/{순서}_{역할}_{산출물}.md`로 남긴다. `.gitignore`에 있어 저장소 문서가 가리키면 안 된다

계약 조회와 게이트가 실패했을 때 볼 것은 `references/`에 있다.

- `references/contract-lookup.md`. 백엔드 계약을 어디서 어떻게 확인하는지
- `references/gate-diagnosis.md`. 게이트마다 자주 걸리는 원인과 고치는 법

## 검사 스크립트

```bash
bash .agents/scripts/check-conventions.sh
```

기계가 판정할 수 있는 것은 여기서 나온다. 리뷰어에게 같은 것을 다시 시키지 않는다. 막는 검사는 걸리면 고치고 판단이 필요한 자리는 해당 리뷰어가 본다.

Stop 훅이 응답을 끝내기 전에 같은 스크립트를 돌린다. 이번 턴에 바뀐 파일이 막는 검사에 걸리면 끝내지 못하고 한 번만 막는다. 게이트 넷은 훅에 넣지 않았다. 빌드가 느리고 타입 검사는 물어보려고 멈추는 자리를 자주 막는다. 게이트는 `AGENTS.md`가 시키고 lefthook이 커밋과 푸시에서 돌린다.

## 보고를 모을 때

막음과 고칠것은 이번에 고친다. 볼것은 묶어 사용자에게 넘긴다. 둘이 어긋나게 말하면 근거 룰을 열어 판정하고 룰이 답하지 않으면 양쪽을 보여주고 묻는다. 같은 것을 둘이 지적하면 하나로 합친다.

## 미결정 항목을 만났을 때

`docs/product/ROADMAP.md`의 미결정 절에 있든 없든 사용자에게 묻는다. 그럴듯한 기본값을 채우지 않고 무엇이 불확실하고 어느 결정을 기다리는지 적는다. 위키 `wiki/decisions/decision-log.md`가 살아 있는 원장이라 ROADMAP보다 최신일 수 있다. **위키는 읽기만 한다.**

## 끝낼 때

`AGENTS.md`의 게이트를 그 순서대로 돌리고 출력을 함께 낸다. **커밋하지 않는다.** 어느 단계도 커밋하거나 푸시하거나 PR을 만들지 않는다.

## 이어서 할 때

- 리뷰 보고를 받아 고치는 중이면 고친 파일만 해당 리뷰어에게 다시 보낸다
- 한 영역만 다시 보라고 하면 그 리뷰어만 부른다
- 남긴 보고가 있으면 먼저 읽고 이미 고쳐진 것은 다시 올리지 않는다

## 막혔을 때

- 에이전트가 실패하면 한 번 다시 부른다. 또 실패하면 그 영역을 확인 못 했다고 적고 넘어간다
- 리뷰어가 열 건을 넘겨 보고하면 부류로 묶어 달라고 다시 요청한다
- 같은 게이트가 세 번 연속 실패하면 시작 직전으로 되돌리고 설계를 다시 본다

## 시나리오 둘

**정상.** 탐색 화면에 정렬 선택을 붙인다. 표면은 같고 동작이 바뀌어 spec-navigator로 SPEC의 정렬 절을 확인하고 implementer가 만든다. 바뀐 것이 `features/popup/ui`와 `className`, 라우트 파일이라 `pop-pick-review-screen`과 `pop-pick-review-tailwind`, `pop-pick-review-nextjs`를 병렬로 부른다. 고칠것 둘을 고치고 tailwind 리뷰어에 그 파일만 다시 보낸다. integration-qa가 경계를 대조하고 게이트를 돌려 끝낸다.

**막힘.** spec-navigator가 응답 필드 이름을 서버 코드에서 확인하지 못해 멈춘다. 지어내지 않고 무엇을 확인 못 했는지 보고한다. 백엔드에 물을 문구를 만들어 사용자에게 넘기고 그 기능은 거기서 멈춘다.
