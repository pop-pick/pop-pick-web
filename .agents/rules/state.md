# 상태 관리

## 규칙

**서버 상태는 TanStack Query, 클라이언트 상태는 Zustand다.** 서버에서 온 데이터를 스토어에 다시 담지 않는다. 로딩과 에러, 캐시를 직접 짜지 않고 쿼리에 맡긴다.

## 어디에 두나

| 상태                                                                                | 두는 곳                           |
| ----------------------------------------------------------------------------------- | --------------------------------- |
| 서버에서 온 것. 팝업 목록과 상세, 코스 결과, 찜한 팝업                              | TanStack Query                    |
| 사용자가 화면에서 고른 것 중 여러 화면이 공유하는 것. 조건 필터, 플래너에 담은 팝업 | Zustand 스토어                    |
| 한 컴포넌트 안에서만 쓰는 것                                                        | `useState`                        |
| 공유와 새로고침 복원이 필요한 조건값                                                | URL 검색 파라미터를 먼저 고려한다 |

URL 검색 파라미터는 프론트엔드 전략의 판단이고 팀 결정은 아니다. 조건 입력값처럼 링크로 넘기거나 새로고침 뒤 되살려야 하는 값이면 스토어보다 먼저 본다.

찜과 플래너 담기는 다르다. 찜은 서버가 로그인 사용자별로 저장하므로 서버 상태이고 쿼리와 뮤테이션으로 다룬다. 플래너에 담은 팝업은 코스를 만들기 전까지만 사는 선택이라 스토어에 둔다. 코스가 만들어지면 서버가 준 코스 ID가 URL에 실리고 그 뒤로는 서버 상태다.

## 이 규칙이 생긴 이유

같은 데이터가 두 곳에 있으면 어긋나고 어느 쪽이 맞는지 알 수 없다. 쿼리가 새 값을 받아도 스토어는 옛 값을 들고 있다. 전역 상태는 조건 필터와 플래너에 담은 팝업 정도로 적을 것이라 스토어는 그만큼만 쓴다.

## 폼

react-hook-form과 zod를 쓴다. 폼 값은 폼이 든다. 스토어에 올리지 않는다. 제출 결과를 다른 화면이 봐야 하면 그때 옮긴다.

## 리뷰에서 볼 것

- 쿼리 결과를 `useEffect`로 스토어에 넣는 코드
- 스토어에 서버 데이터 모양의 필드
- 폼 값을 입력마다 스토어에 쓰는 코드
