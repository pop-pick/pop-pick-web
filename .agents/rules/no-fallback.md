# 오류를 감추지 않는다

## 규칙

**오류를 감싸 빈 값이나 기본값을 돌려주고 호출자에게 성공한 것처럼 보이게 하지 않는다.**

빈 배열과 빈 문자열, 0, 빈 객체는 정상 결과와 모양이 같다. 호출자는 실패를 알 수 없다. 화면은 그려지고 빌드는 통과하고 배포도 끝난다. 사고는 며칠 뒤에 "성수 팝업이 하나도 안 나온다"는 모습으로 돌아온다.

## 이 규칙이 생긴 이유

오류를 감싸 빈 값을 돌려주면 실패가 정상 결과와 같은 모양이 된다. 그 순간에는 아무것도 깨지지 않는다. 화면이 열리고 배포가 나간다. 실패는 배포 뒤에 전혀 다른 모습으로 드러난다. 목록이 비었다거나 추천이 이상하다는 말로 돌아오고 그때는 어디서 실패했는지 추적할 로그도 없다.

감싸고 싶어지는 자리는 대개 설계가 틀린 자리다. 런타임에 실패할 수 있는 읽기를 빌드 타임으로 옮기거나 실패를 타입에 드러내면 감쌀 것 자체가 없어진다.

## 금지하는 것

**실패를 정상 결과와 같은 모양으로 만드는 코드.**

```ts
async function fetchPopups(area: string): Promise<Popup[]> {
	try {
		const res = await fetch(`/api/popups?area=${encodeURIComponent(area)}`);
		return (await res.json()).popups;
	} catch {
		return [];
	}
}
```

그 지역에 팝업이 없는 상태와 서버를 못 읽은 상태가 같은 값이 된다. 목록 화면은 "이 지역에 팝업이 없어요"를 띄우고 플래너는 빈 코스를 만든다.

**비어 있는 catch.**

```ts
try {
	await loadKakaoMapSdk();
} catch {}
```

지도가 비어 있는데 무엇이 실패했는지 아무 데도 남지 않는다.

**파싱 실패를 그럴듯한 기본값으로 메우기.**

```ts
const condition = parsePlannerCondition(searchParams) ?? { area: "성수", hours: 4, companion: "친구" };
```

URL이 깨진 채로 들어온 사용자가 자기가 고른 것과 다른 조건으로 코스를 받는다. 입력 화면으로 되돌려 보냈어야 할 자리다.

**없는 값을 흘려보내기.** `data?.popups?.map(...) ?? []`처럼 물음표를 이어 붙이면 어느 단계가 비었는지 사라진다.

**재시도와 지연으로 미루기.** 의미 없는 `setTimeout`과 임시 플래그, 반복 재시도는 원인을 그대로 두고 증상이 나올 확률만 낮춘다.

## 대신 하는 것

**실패할 수 없는 설계로 바꾼다.** 가장 먼저 볼 선택지다. 값을 빌드 타임에 확정하고 값이 없으면 빌드를 멈춘다. 배포 시점에 정해져 있는 값(환경 변수, 정적 설정, 라우트 목록)을 런타임에 읽어 감싸는 대신 빌드 단계에서 검증한다. 틀린 페이지가 프로덕션에 나가는 것보다 배포가 멈추는 편이 낫다.

**던진다.** Next.js App Router에서 서버 컴포넌트가 던지면 가장 가까운 `error.tsx` 경계가 받는다. 이 저장소에는 아직 `error.tsx`가 없으니 라우팅 뼈대를 잡을 때 함께 만든다. 빌드 타임에 던지면 배포가 멈춘다.

**실패를 값의 타입에 남긴다.** 실패를 값으로 돌려줘야 하면 세 가지를 지킨다. 이름에 적고, 로그를 남기고, 호출자가 분기하게 한다.

```ts
async function fetchPopupsOrNull(area: string): Promise<Popup[] | null> {
	try {
		const res = await fetch(`/api/popups?area=${encodeURIComponent(area)}`, { cache: "no-store" });
		if (!res.ok) {
			console.warn(`[popups] GET ${area} failed: ${res.status}`);
			return null;
		}
		return (await res.json()).popups;
	} catch (error) {
		console.warn(`[popups] GET ${area} network error`, error);
		return null;
	}
}
```

`null`이 반환 타입에 있으니 호출자는 분기해야 한다. 로그가 있으니 무슨 일이 있었는지 남는다. TanStack Query를 붙이면 실패는 `error` 상태로 드러나므로 이렇게 직접 감싸는 자리는 더 줄어든다. 감싸야 할 것처럼 보이면 먼저 쿼리의 에러 상태로 풀 수 있는지 본다.

## 허용되는 축소 동작

기능을 줄여서 계속 동작하게 만드는 것은 감추기와 다르다. 세 조건을 전부 만족할 때만 그렇다.

| 조건                            | 예 (원안 기능 기준. 혼잡도 기능 포함 여부는 8/30 정기회의에서 확정) |
| ------------------------------- | ------------------------------------------------------------------- |
| 제품 결정이고 문서에 적혀 있다  | RUNBOOK에 "혼잡도를 못 받으면 정보 없음으로 보인다"가 적혀 있다     |
| 실패한 상태가 화면에서 구분된다 | 혼잡도 자리에 숫자 대신 "정보 없음"이 뜬다                          |
| 실패가 로그에 남는다            | `console.warn("[congestion] ...")`                                  |

로그가 빠지면 감춘 것이다. 화면 구분이 빠지면 틀린 값을 사실처럼 보여주는 것이다.

**흡수한 실패가 아래 단계에서 다시 뭉개지는 자리를 조심한다.** `fetchPopupsOrNull`이 `null`을 제대로 돌려줘도 그 위에서 `?? []`로 받으면 "팝업 없음"과 "팝업 모름"이 같아진다. `null`은 화면까지 살아가야 한다.

## 리뷰에서 볼 것

- `catch` 블록이 값을 돌려주면 그 값이 정상 결과와 구분되는가
- 비어 있는 `catch`가 없는가
- `?? []`와 `?? 0`, `?? ""`가 실패를 삼키고 있지 않은가
- 새로 감싸려는 호출을 빌드 타임으로 옮길 수 있는가. 옮길 수 있으면 감싸지 말고 옮긴다
