# 테스트

## 전략

**테스팅 트로피 하나로 간다.** 층은 아래에서부터 정적 분석과 단위, 통합, e2e다. 비율 목표를 세우지 않는다. 판정 대상은 개수가 아니라 "이 테스트가 빨간불을 냈을 때 무엇이 깨졌는지 이름으로 말할 수 있는가"다.

**정적 분석 층은 이미 셋이 서 있다.** `pnpm type:check`와 `pnpm lint`, `pnpm format:check`다. 이 셋이 막는 것을 테스트로 다시 확인하지 않는다.

**기본 동작은 삭제다.** 테스트를 새로 만들기 전에 같은 것을 보는 기존 테스트가 있는지 먼저 읽는다. 스위트가 커지면 늘리는 대신 줄인다. 남기는 테스트에는 "이게 깨지면 무엇이 조용히 잘못되는가"를 한 문장으로 댈 수 있어야 한다.

## 도구

단위와 컴포넌트, e2e 도구는 미정이다. 지금 저장소에는 테스트 실행 명령이 없다.

도구를 도입하면 이 절에 셋을 적는다.

- 도구 이름과 버전
- 실행 명령. `package.json`의 스크립트 이름으로 적는다
- 파일 위치 규칙. 대상 코드 옆에 두는지, 별도 디렉터리에 모으는지

도구 도입은 의존성 추가라서 사용자 승인이 필요하다. 아래 절의 원칙은 도구와 무관하게 적용되며 도구 이름이 들어가야 할 자리는 도입 시점에 구체화한다.

## 값이 나는 자리

공통 성질은 하나다. 틀려도 화면이 그려지고 빌드가 통과한다.

아래 표는 원안 기능 기준 예시다. 기능 범위는 8/30 정기회의에서 확정되므로 그 뒤에 실제 기능에 맞춰 고친다.

| 자리                       | 예                                                    | 틀리면                                                       |
| -------------------------- | ----------------------------------------------------- | ------------------------------------------------------------ |
| 분기 있는 순수 함수        | 코스 방문 순서와 예상 소요시간 계산                   | 동선이 뒤바뀐 코스가 그려지고 화면은 정상이다                |
| 날짜 파생값                | 팝업 기간에서 진행 중과 종료, 오픈 예정을 가르는 계산 | 끝난 팝업이 진행 중으로 뜬다                                 |
| 입력 검증 스키마           | 조건 입력 폼의 zod 스키마 경계값                      | 걸러야 할 입력이 통과해 요청이 서버에서 실패한다             |
| 기계만 읽는 산출물         | sitemap과 robots, 메타 태그                           | 며칠 뒤 유입이 줄어드는 모습으로 돌아온다                    |
| 브라우저에서만 드러나는 것 | 포커스 순서와 키보드 조작, 모션 축소                  | 브라우저 없는 환경은 보지 못한다. 배포 뒤 사용자가 먼저 본다 |

## 값이 적은 자리

화면 배치만 하는 컴포넌트의 렌더 확인, 상수를 그대로 다시 적는 단언, 배럴과 재노출의 형태 확인, 라이브러리가 하는 일의 재확인이다.

## 층마다 소유하는 것

같은 보장을 두 층이 함께 보면 하나를 지운다. 어느 쪽을 지울지는 아래로 정한다.

**단위와 컴포넌트가 소유한다.** 우리가 직접 짠 로직이다. 이벤트 짝짓기, 상태 전이, 분기 있는 순수 함수, 파생값 계산. 배경 클릭과 안쪽 클릭을 가려내는 판정이나 겹친 대화상자의 잠금 수를 세는 로직이 이 자리다.

**e2e가 소유한다.** 브라우저 없는 환경이 흉내내지 못하는 것만이다. 실제 Tab 순회 순서, 실제 포커스 복귀, 스크롤바로 인한 가로 밀림, 배경 요소의 포커스 차단, `@media print`, 모션 축소, 클립보드, 자바스크립트를 끈 응답 HTML.

**둘 다 아니면 둘 다 지운다.** native `<dialog>`의 ESC 닫기와 `aria-modal` 부여는 브라우저 동작이라 어느 층도 확인하지 않는다.

## 지우는 기준

하나라도 걸리면 삭제 후보다.

1. 구현 상세를 단언한다. 내부 상태, 클래스명, DOM을 직접 뒤지는 조회, 호출 횟수
2. role이나 텍스트로 잡을 수 있는데 test id로 잡는다
3. 하위 층이 이미 같은 보장을 낸다. 지울 때 그 파일과 케이스 이름을 근거로 댄다
4. 같은 부류를 여러 개 두고 있다. 부류마다 하나면 충분하다
5. 정적 분석 셋 중 하나가 이미 막는다
6. 상수나 설정값을 그대로 다시 적는다
7. 라이브러리나 프레임워크가 하는 일을 확인한다
8. 요청 가로채기 도구로 요청이 발생했는지나 요청 형태를 단언한다
9. 스냅샷이다
10. async 서버 컴포넌트를 렌더해 단언한다. Next 문서가 e2e로 하라고 명시한다
11. 사용자 동작을 흉내내는 유틸리티가 있는데 DOM 이벤트를 직접 발사하거나 렌더 갱신을 손으로 감싼다
12. 단언 없이 조회만 하거나 항상 참인 단언이다
13. e2e인데 브라우저가 필요 없다

도구를 도입하면 1번과 8번, 11번을 그 도구의 API 이름으로 구체화한다.

## 지우면 안 되는 것

지우는 기준에 걸려도 아래에 함께 걸리면 지우지 않고 고친다.

1. 틀려도 화면이 그려지고 빌드가 통과하는 자리
2. 실제로 깨진 적이 있고 사고 기록이 있다. 케이스 이름에 그 사고를 적어 둔다
3. 브라우저에서만 드러난다
4. 자동 규칙 검사가 못 잡는 접근성이다. 포커스 순서와 키보드 조작, 포커스 갇힘, 랜드마크
5. 데이터가 정책대로 걸러지는가를 본다
6. 분기가 있는 순수 함수의 경계값이다
7. 실패를 값으로 돌려주는 계약을 지키는가를 본다. `no-fallback.md`가 정한 축소 동작
8. 부류에서 마지막 하나다
9. 테스트 도구의 지시문 주석이 붙어 있다. 케이스를 지우다 파일 머리를 함께 지우지 않는다. 지시문의 종류는 `comments.md`에 있다
10. 다른 테스트가 쓰는 공유 자산이다. 공통 설정과 헬퍼, 테스트용 데이터

## 지울 때 확인하는 것

1. 지우려는 케이스가 검사하는 대상 코드를 실제로 연다. 이름만 보고 판정하지 않는다
2. "지우고 그 코드를 망가뜨리면 무엇이 잡는가"를 답한다. 아무것도 못 잡으면 그 테스트는 값이 있다
3. 하위 층 중복이 근거면 그 파일과 케이스 이름을 확인한다. 같은 작업에서 그쪽을 지우고 있지 않은지 마지막에 다시 본다
4. 지운 뒤 게이트를 전부 돌린다
5. 커버리지를 전후로 대조한다. 목표 수치로 삼지 말고 급락한 자리가 있는지만 본다. 많이 지웠는데 커버리지가 거의 그대로면 지운 것이 중복이었다는 뜻이다

## 하지 않기로 한 것

커버리지 수치 목표를 세우지 않는다. 수치가 목표가 되면 값이 적은 자리에 테스트가 쌓인다.
