# 구현

계획이 정한 파일 안에서 만든다. 계획에 없는 파일을 건드려야 하면 멈추고 왜인지 보고한다.

## 순서

데이터 층을 먼저 만들고 화면이 그 층의 타입과 훅을 쓴다. `features/{기능}/api/{동작}.ts`에 엔드포인트 하나씩, `hooks/use{동작}.ts`에 변경 훅, `model/`에 스토어와 순수 함수와 타입, `ui/`에 컴포넌트를 둔다. 라우트 파일은 조립만 한다.

## 읽는 것

룰은 고치는 파일에 맞춰 실린다. 새로 만드는 파일에는 훅이 맞는 룰 목록을 알려 주니 읽지 않은 룰은 열고 시작한다. 화면 배치는 `docs/design/DESIGN-SPEC.md`, 받은 토큰과 임시 값의 현황은 `docs/design/DESIGN.md`다.

## 지어내지 않는 것

응답 필드 이름이다. `../pop-pick-server/`의 해당 feature 패키지에서 확인한 것만 쓴다. 확인할 수 없으면 거기서 멈추고 무엇을 확인 못 했는지 보고한다.

## 막히면 자문한다

`Agent` 도구로 부르고 질문 하나와 그 값이 쓰이는 파일을 넘긴다. 답으로 받은 토큰과 이름대로 만든다.

| 막힌 것                                | 부를 리뷰어                 |
| -------------------------------------- | --------------------------- |
| 시안 값을 어느 토큰으로 옮길지         | `pop-pick-review-tailwind`  |
| 파일을 어디에 둘지                     | `pop-pick-review-structure` |
| 값을 쿼리와 URL, 스토어 중 어디에 둘지 | `pop-pick-review-data`      |

임의값으로 먼저 만들고 나중에 고치지 않는다.

## 끝낼 때

`AGENTS.md`의 게이트를 그 순서로 돌리고 출력을 함께 낸다. 걸리면 고친다. 검사를 느슨하게 고쳐서 통과시키지 않는다.

## 하지 않는 것

- 커밋과 푸시
- 백엔드 저장소 수정. 고칠 것이 보이면 무엇을 왜 고쳐야 하는지 보고만 한다
- 의존성 추가와 기성 UI 라이브러리 설치. 필요해 보이면 먼저 묻는다
- 컴포넌트 안에서 `fetch` 직접 부르기
